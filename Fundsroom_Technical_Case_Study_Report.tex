\section{Executive Summary \& Business Context}
Wholesale and distribution organizations operate in high-throughput environments where disparate departments—\textbf{Sales, Warehouse, Accounts, and Executive Management}—require synchronized visibility into customer relationships and real-time physical inventory.

Without a unified Enterprise Resource Planning (ERP) and Customer Relationship Management (CRM) system, distributors face severe operational bottlenecks:
\begin{enumerate}[itemsep=0.2em]
    \item \textbf{Negative Stock Overselling:} Multiple sales representatives inadvertently selling the same warehouse items concurrently.
    \item \textbf{Lost Account History:} Overwritten or untracked commercial discussions with wholesale buyers.
    \item \textbf{Invoice Inaccuracies:} Delivery slips reflecting modified catalog prices rather than the agreed price at the moment of dispatch.
\end{enumerate}

This project delivers a complete, production-grade, full-stack Operations Portal addressing these challenges using a \textbf{Node.js / Express / TypeScript} backend, \textbf{PostgreSQL} ACID transactions with pessimistic row-locking, and a responsive \textbf{React 18 / Vite / TypeScript} frontend.

\begin{verbatim}
[ React 18 + Vite SPA ]  <--->  HTTPS / JWT Bearer Tokens
          |
          v
[ Express.js + TypeScript API ]
   ├── Auth & RBAC Middleware (requireAuth, requireRole)
   ├── Controllers (CRM, Inventory, Challans, Dashboard)
   └── Connection Pool (pg Pool with TLS/SSL handling)
          |
          v  ACID Transactions + Row-Locking (SELECT ... FOR UPDATE)
[ Cloud PostgreSQL Instance (Neon.tech Serverless) ]
   ├── Relational Tables (users, customers, products, challans, etc.)

\end{verbatim}

% --- 3. Core Functional Modules ---
\section{Core Functional Modules}

\subsection{Authentication \& Role-Based Access Control (RBAC)}
The system defines four discrete employee personas, enforced at both the client route guards and backend API endpoints:
\begin{itemize}[itemsep=0.3em]
    \item \textbf{Admin:} Unrestricted administrative control across CRM, inventory catalogs, Challans, and personnel.
    \item \textbf{Sales:} Management of customer accounts, follow-up timeline entries, and draft/confirmed sales challan generation.
    \item \textbf{Warehouse:} Real-time physical inventory monitoring, storage rack tracking, and manual stock movements (\texttt{IN}/\texttt{OUT}).
    \item \textbf{Accounts:} Read-only auditing of delivery challans, gross revenue summaries, and printable dispatch slips.
\end{itemize}

\subsection{Customer CRM Module}
\begin{itemize}[itemsep=0.3em]
    \item \textbf{Customer Master:} Tracks firm name, contact person, mobile, email, GSTIN, customer type (\textit{Retail, Wholesale, Distributor}), dispatch address, and pipeline status (\textit{Lead, Active, Inactive}).
    \item \textbf{Append-Only Follow-Up Timeline:} Rather than overwriting notes, sales representatives log interactions into an immutable timeline, attributing notes to the authenticated author with exact timestamps.
    \item \textbf{Search \& Pagination:} Dynamic multi-field database indexing over business names, phone numbers, and contact names.
\end{itemize}

\subsection{Product Catalog \& Inventory Module}
\begin{itemize}[itemsep=0.3em]
    \item \textbf{Inventory Tracking:} Tracks SKU codes, categories, unit prices, storage bays (\textit{e.g., Bay A-1, Rack 03}), on-hand stock, and minimum stock alerts.
    \item \textbf{Low-Stock Threshold Engine:} Dynamic visual warnings for products falling below safety thresholds.
    \item \textbf{Stock Movement Audit Log:} Mandatory audit logging for every inventory adjustment, recording movement type (\texttt{IN}/\texttt{OUT}), quantity, reason, and employee ID.
\end{itemize}

\subsection{Sales Challan Engine}
Enables sales personnel to select a customer, assemble multi-item product rows, calculate live subtotals, and either:
\begin{enumerate}[itemsep=0.2em]
    \item \textbf{Save as Draft:} Records intent without altering warehouse inventory.
    \item \textbf{Confirm Challan:} Triggers atomic stock deductions and generates an immutable delivery slip.
\end{enumerate}

% --- 4. Deep-Dive: Concurrency & Pessimistic Locking ---
\section{Critical Engineering: Concurrency \& Stock Deduction}

\subsection{The Problem: Race Conditions \& Negative Stock}
In high-volume wholesale operations, concurrent checkouts for high-demand goods pose severe integrity risks. If two sales representatives simultaneously confirm orders for an item with only 5 units in stock (ordering 4 and 3 units respectively), naive architectures read the stock concurrently, approve both orders, and leave inventory at $-2$.

\subsection{The Solution: Pessimistic Row-Locking (\texttt{SELECT ... FOR UPDATE})}
The delivery challan confirmation engine guarantees absolute stock integrity through strict database transactions:

\begin{lstlisting}[language=SQL, caption={Pessimistic Row-Locking Stock Deduction Transaction}]
BEGIN;

-- 1. Lock rows ordered by primary key to prevent distributed deadlocks
SELECT id, name, sku, unit_price, current_stock 
FROM products 
WHERE id = ANY($1::int[]) 
ORDER BY id ASC 
FOR UPDATE;

-- 2. Verify stock sufficiency inside the locked transaction state
-- IF current_stock < requested_quantity:
--    ROLLBACK;
--    RETURN HTTP 400 Bad Request ("INSUFFICIENT_STOCK");

-- 3. Deduct stock safely
UPDATE products 
SET current_stock = current_stock - $qty, updated_at = CURRENT_TIMESTAMP 
WHERE id = $productId;

-- 4. Record stock movement audit entry
INSERT INTO stock_movements (product_id, quantity_changed, movement_type, reason, created_by)
VALUES ($productId, $qty, 'OUT', 'Sales Challan ' || $challanNumber, $userId);

-- 5. Commit atomic transaction
COMMIT;
\end{lstlisting}

\subsection{Snapshot Integrity}
To prevent historical accounting distortions when product catalog prices change, \texttt{challan\_items} stores an immutable snapshot of \texttt{product\_name}, \texttt{product\_sku}, and \texttt{unit\_price} at the exact millisecond of sale.

\section{Postman Collection \& Verification Plan}
The root repository includes a Postman v2.1 test collection (\texttt{postman\_collection.json}) covering all 17 REST API endpoints:
\begin{itemize}[itemsep=0.3em]
    \item \textbf{Automated Authentication:} Running any login endpoint captures the JWT bearer token into collection variables automatically.
    \item \textbf{CRM \& Product Flows:} Creation, query filters, and follow-up timeline submissions.
    \item \textbf{Transaction Success Verification:} Creating a confirmed challan verifies HTTP 201 status and immediate stock deduction.
    \item \textbf{Transaction Insufficient Stock Verification:} Submitting a challan with quantity $999{,}999$ returns HTTP 400 Bad Request (\texttt{INSUFFICIENT\_STOCK}), confirming database rollback.
\end{itemize}

% --- 7. Known Limitations & Future Roadmap ---
\section{Known Limitations \& Future Roadmap}
\begin{enumerate}[itemsep=0.3em]
    \item \textbf{Automated Tax Calculations:} The current challan engine calculates gross item totals. A production enhancement would compute split CGST/SGST (intra-state) or IGST (inter-state) based on customer state codes.
    \item \textbf{Purchase Order Ingest:} While stock adjustments allow manual inward entries, an automated Purchase Order to Goods Receipt Note (GRN) pipeline would streamline supplier intake.
    \item \textbf{Server-Side PDF Generation:} Challan printing currently utilizes browser rendering (\texttt{window.print()}); headless Puppeteer integration can generate downloadable binary PDFs for automated emailing.
\end{enumerate}
